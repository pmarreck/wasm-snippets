# Repository Guidelines

Use this guide to work efficiently within the wasm-snippets playground (quicksort, demos, and helpers).

## Project Structure & Module Organization
- `scripts/` contains runnable modules like `quicksort` (WAT with a wasmrun shebang).
- `scripts/wasmbuild` compiles `.wat`/shebang sources; `scripts/wasmrun` launches them with the selected runtime.
- `wat/` now just holds build caches (`wat/build/`).
- `tests/` hosts fixtures and `run.sh`; `test` is the entry point used by CI scripts.
- `data/` provides sample and benchmark payloads, while `build/` caches compilation artifacts.
- `bench`, `build_all`, and `demos/` expose reproducible benches, bulk builds, and exploratory WASI examples.

## Build, Test, and Development Commands
- `nix develop` (or `direnv allow`) loads the dev shell with Wasm toolchains.
- `./build_all` compiles every module and pre-populates caches (set `WASM_BUILD_CACHE=out/` to override).
- `./test` runs `tests/run.sh` against GNU `sort` for C and en_US locales.
- `./bench` executes runtime benchmarks; use `RUNS=50 ./bench` for longer samples.
- `scripts/wasmbuild scripts/quicksort` and `scripts/quicksort < data/sample_unsorted.txt` are useful for quick iteration.

## Coding Style & Naming Conventions
- Use two-space indentation in WAT blocks and align S-expressions for readability.
- Name functions and labels with lowercase snake case (e.g. `$apply_collate_value`) to match existing modules.
- Keep scripts POSIX shell compatible; prefer descriptive, hyphen-free filenames (e.g. `wasmbuild`).
- Run formatting tools already embedded in scripts; avoid introducing language-specific formatters unless discussed first.

## Testing Guidelines
- Extend `tests/run.sh` when adding behaviours; mirror new fixtures under `tests/` or `data/`.
- Ensure quicksort output matches native `sort` for `LC_ALL=C` and `LC_ALL=en_US.UTF-8`.
- Practice TDD strictly: add or update a failing test first, implement the minimal fix, then rerun `./test` before committing.
- Add new regression cases as newline-delimited inputs and cover both cache-hit and cache-miss paths.
- Document any new environment variables in `README.md` and ensure `./test` passes without manual setup.

## Commit & Pull Request Guidelines
- Ship one feature or fix per branch, and build each iteration on a green test run to keep reviews focused.
- Follow the existing short, present-tense style (`git log` shows “the version that worked via Rust”); aim for messages under 72 characters.
- Reference related issues in the body, outline test coverage (`./test`, `./bench`, etc.), and include reproduction steps for bugs.
- For PRs, link benchmarks or screenshots when UI/CLI output changes, and note locale-specific expectations.
- Keep changes scoped: WAT, scripts, and fixtures should update together so reviewers can validate behaviour end-to-end.

## Environment & Tooling Tips
- Nix flakes pin the toolchain; update `flake.lock` only when bumping dependencies intentionally.
- Avoid committing built artifacts from `build/`; they are cache outputs regenerated by the provided scripts.
- Set `LC_ALL` explicitly when sharing repro commands to avoid locale drift between systems.
